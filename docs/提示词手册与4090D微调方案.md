### 关键规律

- **输入**：绝大多数是**结构化 JSON**（数字孪生、`<input_data>`、payload）包进 user prompt；会诊问答类是自由文本拼接块（意图 / 患者上下文 / RAG / 历史）。
- **输出**：**JSON 占绝对主流**（`response_format=json_object` 或 prompt 内嵌 schema）；自然语言仅用于会诊 7 栏、语音摘要、润色、营养 / 质控短摘要。
- **超大 prompt**（微调重点观察对象）：`nurse_bedside_handover.md`（6212 字）、`voice_rounding` 校对（约 3400）、MDT `MODERATOR`（约 3200）、`WARD_ROUND`（约 3000）、MDT `SPECIALIST_TEMPLATE`（约 2600 + 角色块）、`ai_risk`（约 2300）、`clinical_reasoning SYSTEM`（约 2100）。
- **公共拼接件**：`LLM_PROMPT_SOURCE_RULES`（`prediction_contract.py:733`，预测来源守则）会追加到临床推理三阶段、文书生成、I-PASS 交班的 prompt 尾部——所有微调样本必须包含这份守则，否则训练/推理契约不一致。

## 三、整理发现：现有契约 vs 微调方案的 3 个冲突点

把全库提示词与「重症微调数据集架构」对照后，有三处必须先统一，否则微调白做：

1. **"严格 JSON、禁止任何额外文本" vs "先 CoT 后 JSON"**
   现网绝大多数 prompt 要求 `严格输出 JSON，不要输出任何额外文本`；而微调方案要求强制 CoT 在 JSON 之前（否则 7B/14B 准确率下降 30%+）。
   **建议**：JSON 内新增 `reasoning` 字段承载临床逻辑推导（如 `"reasoning": "1. 休克性质判断…2. SOFA…"`)，`response_format=json_object` 不变，下游解析不受影响。只改数据与少量 prompt，不动消费端。

2. **微调样本 system 与线上 system 不一致**
   `prepare_data.py` 给所有样本硬编码同一个 3 行 system，但线上 61 条 prompt 各有各的 system。
   **建议**：样本必须**按调用方还原原 system**（从对应模块提取），并附带 `LLM_PROMPT_SOURCE_RULES` 尾巴。统一的应该是**角色认知与输出契约**，不是字面 system。

3. **数据源太窄**
   `prepare_data.py` 只从 `ai_consult_logs` 拉（占 61 条中的 5 条），文书、交接班、警报推理这些 JSON 重灾区没有样本。
   **建议**：按模块分层采样（见下表），每条样本记录 `prompt_module` 元数据，便于分组评估。

### 微调优先级分层（按调用频率 × 输出复杂度 × 临床风险）

| 层级 | 模块 | 策略 |
|---|---|---|
| **T0 必微调** | 临床推理 SPAR、警报根因/风险评估、文书 6 模板、交接班医生/床旁 | 高频 + 严格 JSON + 数值零编造；用黄金样本 500–1500 条 SFT |
| **T1 优先微调** | MDT 专科 + 主持人、查房记录、会诊 7 栏 | schema 复杂、长输出；微调对格式稳定收益大 |
| **T2 Prompt 工程即可** | 首屏预览、Pulse 播报、营养、润色、质控摘要 | 输出短、容错高；靠 few-shot 与温度控制 |
| **T3 保留 RAG/规则** | 入排解析、阈值建议、预警规则推荐 | 结构化程度极高，规则+校验比生成更可靠；模型只做草稿 |

## 四、4090D（24GB 内网卡）落地方案

### 4.1 选型

| 用途 | 模型 | 理由 |
|---|---|---|
| 主力微调/推理基座 | **Qwen2.5-14B-Instruct** | 4090D 24GB：QLoRA 训练可行（4bit 约 9GB + 激活，seqlen 4k batch 1–2）；推理用 AWQ/GPTQ 4bit 约 8.5GB，vLLM 单实例轻松放下，还剩显存给 KV cache |
| 强推理备选 | DeepSeek-R1-Distill-Qwen-14B | 休克鉴别、MODS 病因链等需要长逻辑链的场景；同为 Qwen 架构可复用数据 |
| 轻量兜底 | Qwen2.5-7B-Instruct | 想要更高吞吐或并发两个实例时的降级选项 |
| 边缘/床旁 | Qwen2.5-1.5B | 不做诊断决策，只做报警分类、字段提取（现有 61 条里 T2 层可下放） |

**单卡注意**：4090D 只有一张，训练时不能同时服务。建议**错峰**：白天 vLLM 对外服务，夜间窗口跑 QLoRA；或训练用 7B、服务用 14B。

### 4.2 训练（QLoRA，单卡）

复用现有骨架 `backend/scripts/lora_finetune/`，按第三节修订数据管线：

1. **数据准备**：扩展 `prepare_data.py`，按 T0/T1 模块分层采样（`ai_consult_logs` + 文书生成日志 + 交接班生成日志 + 推理调用日志），每条还原**该模块原 system**、追加 `LLM_PROMPT_SOURCE_RULES`、脱敏（沿用 `deidentify_text`）、JSON 有效性校验。目标 500–1500 条黄金样本起步。
2. **格式**：ChatML `messages`（项目已在用），assistant 内容 = `【临床逻辑推导】…\n【结构化决策输出】\n```json…``` ` 或 `reasoning` 字段内嵌版（与线上契约统一后二选一）。
3. **训练**：`LLaMA-Factory` QLoRA——`r=16~32, alpha=64, lr=1e-4~2e-4, epochs=2–3, max_len=4096, gradient_checkpointing`；4090D 一轮（千条级）约 1–3 小时。
4. **边界反例**：按微调方案注入矛盾数据（如 MAP 55 却标"循环稳定"→ 输出拒绝/报错），并做数值一致性测试（输出中的每个数字必须能在输入中找到）。
5. **评估**：`evaluate.py` 扩展为分模块双盲打分——JSON 可解析率、schema 字段完整率、数值零幻觉率、临床逻辑专家评分。

### 4.3 推理接入现网

```bash
vllm serve Qwen2.5-14B-Instruct-AWQ \
  --host 0.0.0.0 --port 8001 \
  --max-model-len 8192 \
  --gpu-memory-utilization 0.85
```

现网 `llm_runtime.py` 已支持环境变量路由，内网接入只需：

```bash
LLM_BASE_URL=http://<4090D内网IP>:8001/v1
LLM_MODEL=Qwen2.5-14B-Instruct-AWQ
LLM_FAST_MODEL=Qwen2.5-14B-Instruct-AWQ          # 同卡单实例时指向同一模型
LLM_REASONING_MODEL=Qwen2.5-14B-Instruct-AWQ
LLM_MODEL_MEDICAL=Qwen2.5-14B-Instruct-AWQ
LLM_API_KEY=unused
```

> 若以后加第二张卡/一台机：`LLM_FAST_MODEL` 指 7B 实例、`LLM_REASONING_MODEL` 指 14B 实例，`llm_runtime.py` 的 provider 选择逻辑无需改代码。

灰度建议：先只把 **T0 的 2–3 个低风险调用点**（预警解释润色、质控摘要、文书草稿）切到微调模型，跑 1–2 周数值一致性指标，再放临床推理与交班。

### 4.4 内网合规

- 4090D 完全内网 + 模型权重本地存放，满足"数据不出院"；微调语料沿用现有 `deidentify_text` + `whitelist_payload` 脱敏与 `lora_training_corpus_audit` 审计表。
- 微调样本继续写审计记录（`prepare_data.py --write-audit`），保留 `source_hash` 可追溯到原始日志。
